## 1. XEQM Labs 是什么

XEQM Labs 是一家隐私技术公司。其旗舰产品 EXIOM 是一个隐私保护的权益证明 Layer 1 网络和商业开发者平台，由全球一组服务节点运营。XEQM 是该平台的访问和使用代币。开发者可免费构建，并以 XEQM 支付生产使用费用，随着调用 API 而消耗。服务节点运营者通过保护网络赚取 XEQM，同一批运营者还可通过运行为平台 oracle 产品服务的 oracle sidecar 赚取额外收入。

该项目承载着一段超过七年的社区和运营历史。EXIOM 主网的构建旨在为该社区提供一个具有可验证供应量、可预测发行计划、无工作量证明组件的纯权益证明共识，以及尊重运营者时间和资本的服务节点机制的网络。

XEQM 是原生 Layer 1 代币，未在任何其他链上代币化，不是 ERC-20 或封装资产，也没有跨链桥接。持有者直接与 EXIOM 主网交互。

### EXIOM 产品家族

**EXIOM 服务节点网络。** 已在主网上线。一组全球服务节点保护链安全、赚取区块奖励，并构成所有其他 EXIOM 产品运行所依托的基础设施层。截至 September 27, 2026 有 943 个活跃服务节点。

**EXIOM 代币互换。** 一款商业产品，使项目能够以完全的加密可审计性将其持有者社区从旧链迁移到新链。试点是将 XEQ 持有者迁移到 EXIOM 主网上的 XEQM，运行了 35 天，每笔提交都通过带有公开 SHA256 指纹的加密验证账本处理。该产品可供其他需要可验证链迁移的项目使用。

**EXIOM Oracle。** 已在主网上线。平台的首款 oracle 产品：一个由 XEQM 服务节点运营者组成的委员会 — 每人运行一个轻量级 oracle sidecar — 生成 BLS 聚合、EIP-712 签名的合规证明（例如，某地址符合给定司法管辖区的资格），应用程序通过开发者 API 使用这些证明。它部署在 Robinhood Chain（chainId 4663）上，截至 September 28, 2026 运行一个 12 名成员的运营者委员会。运行 sidecar 是服务节点运营者在区块奖励之上赚取额外、基于使用量收入的方式。

**EXIOM 开发者 API。** 测试版已上线。一个结构化的 API，公开平台的合规和验证能力 — 签名合规声明和验证引擎（签名声明、TLSNotary 和零知识机制）— 具有自助访问（一个 DID 加 API 密钥）、OpenAPI 3.1 规范、webhooks 和幂等请求。开发者在慷慨的月度额度内免费构建，并以 XEQM 按调用支付生产使用费用。Phase 2，进行中。

**EXIOM Privacy Oracle。** 已设计，基础设施已就位。oracle 的更广泛演进：证明关于私有网络数据的事实（通过 TLSNotary 和零知识技术），而不暴露底层来源。支撑它的验证引擎和 oracle 会话端点已经上线；完整的私有网络数据 oracle 是 Phase 3 的交付物。EXIOM RFQ 平台和第三方应用程序都可以使用 oracle 输出。

**EXIOM RFQ 交易平台。** 开发中。一个具有加密结算证明的点对点场外交易平台，基于 EXIOM API 构建。首个交易对是 XEQM/BTC，二者均为原生 Layer 1 资产，无代币化、无封装、无跨链桥风险。oracle 为定价层提供私有价格证明。Phase 2/3。

XEQM Labs 将 EXIOM 作为商业软件平台运营。目标是实现可持续的平台收入，随时间减少对治理发行的依赖。XEQM Labs 不鼓励基于投机性价格升值购买 XEQM。

## 2. 供应来源

迁移已完成。276,917,604 XEQM 在 EXIOM 主网上发行以换取旧有持仓。该数字是 May 6, 2026 主网启动时经过验证的起始供应量。每一笔旧有存入都记录在带有 SHA256 指纹的公开账本中。新链在互换结束时一次性铸造，以匹配该精确的已验证总量。互换所涉每个钱包的花费密钥均已公布，任何人都可以验证从存入到支付的完整交易历史。

除起始供应量外，新的 XEQM 通过两个协议级发行流进入流通：服务节点区块奖励和治理发行。两者都按写入协议的固定且可预测的计划运行，任何人都可以根据公开参数计算。费率和运营细节见 Section 3。总供应量随时间增长。XEQM 是一条无供应上限的链，采用与 Monero 尾部发行相同的模型。该项目所承诺的固定供应纪律指的是不存在自由裁量的发行，而非对协议驱动发行的硬性上限。

**无自由裁量铸造。** 协议不允许临时发行、手动供应调整或计划外铸造。每一枚进入流通的新 XEQM 都通过上述两个计划发行流产生。

**无销毁。** 该网络所构建的加密架构不支持通常意义上的可证明销毁。任何代币发送到的地址，其不可花费程度仅取决于密钥被可证明地销毁的程度。我们不会将任何钱包表述为销毁地址。在迁移窗口期间未互换的代币仍留在非活跃的旧链上，不属于 XEQM 供应量。

## 3. 代币经济学模型

### 区块发行

网络每 60 秒产生一个新区块，向选定的服务节点奖励 8.25 XEQM，每天产生 11,880 XEQM。在 943 个活跃节点（September 27, 2026）的情况下，每个节点每天赚取约 12.6 XEQM，或每月约 380 XEQM。

从 HF21 开始，区块奖励按每周批处理计划分发。在 HF21 之前，奖励每 20 个区块发放一次。奖励现在在每个 10,080 区块窗口（约 7 天）内累积，并在每个窗口结束时支付。总发行率不变；只是支付节奏发生了变化。

### 治理发行

国库每天收到约 17,857 XEQM，或每周约 124,999 XEQM。这是一个活跃的商业软件开发团队的运营预算。在平台实现收入之前，工程师、安全审查人员、基础设施运营者和生态系统贡献者都从该发行中获得报酬。随着每个 EXIOM 产品达到可创收状态，治理发行将相应地进行审查和削减。长期目标是让平台收入取代治理发行成为主要的资金来源机制。

### 发行分配

| 分配 | 份额 | 用途 |
|---|---|---|
| 服务节点奖励 | 40% | 直接支付给服务节点的区块奖励 |
| 核心协议开发 | 25% | 区块链、EXIOM 平台和核心网络服务 |
| 营销和推广 | 15% | 网络知名度和采用 |
| 生态系统和社区 | 10% | 资助、赏金、社区奖励、集成支持 |
| 安全和审计 | 5% | 审计、安全审查、可靠性测试 |
| 长期储备 | 5% | 稳定性、紧急需求、长期运营 |

### EXIOM 平台收入与分配

除区块奖励外，平台还从开发者使用中赚取收入。访问采用预付费：开发者通过存入 XEQM（不可退还）为其账户充值，该余额随着他们按调用计价消耗生产 API 而被扣减。在免费额度内的开发和评估不收费。

被消耗的 XEQM 被确认为平台收入，并在服务 oracle 的运营者和平台运营之间分配：

| 接收方 | 份额 | 用途 |
|---|---|---|
| Oracle sidecar 运营者 | 70% | 运行 oracle sidecar 的服务节点运营者，按其帮助服务的 oracle 职责比例获得奖励 |
| 平台运营和开发 | 30% | 为持续的运营和开发提供资金，随时间减少对治理发行的依赖 |

运营者占大头，因为他们运行服务 oracle 的基础设施。70/30 比例是初始值，可通过治理调整。收入按与区块奖励相同的每周节奏确认和分配 — 每个 10,080 区块窗口（约 7 天），与 HF21 奖励批处理对齐 — 因此运营者在同一个节奏上获得区块奖励和使用收入份额。这一收入分成是 Section 4 所述运营者 sidecar 奖励从真实使用而非发行中获得资金的机制。

运行服务节点（及其 oracle sidecar）的基准硬件：4 个 CPU 核心、8 GB RAM、100 GB SSD、100 Mbps 连接。更重的隐私 oracle 工作负载需要更高配置，见 Section 10。

## 4. 服务节点结构

### 质押参数

| 参数 | 值 |
|---|---|
| 完整节点要求 | 200,000 XEQM |
| 最低运营者质押 | 100,000 XEQM（完整要求的 50%） |
| 最高运营者费用 | 10% |
| 解绑期，自愿退出 | 14 天，奖励继续 |
| 解绑期，强制注销 | 14 天，无奖励（在 HF22 中统一） |
| 最大贡献者槽位 | 11（含运营者） |
| 每槽位最低社区贡献 | 10,000 XEQM |
| 每节点社区质押者窗口 | 最多 100,000 XEQM，分布于最多 10 个贡献者槽位 |

### 节点经济学

许多云 VPS 提供商提供免费服务层级，可以零月度成本支持服务节点运营。一个约 $5.28 每月的付费 VPS 可以运行 10 个服务节点，使每节点托管成本约为 $0.53 每月。通过 Pecunia 的托管服务可用，价格为每节点每月 $1.76。

每节点区块奖励与活跃节点数量成反比缩放：在 943 个活跃服务节点（September 27, 2026）的情况下，网络每天 11,880 XEQM 的发行量折算为每节点每天约 12.6 XEQM，每月约 380 XEQM。由于奖励和质押都以 XEQM 计价，区块奖励 APY 约为 2.3%，与价格无关；托管是唯一重要的经常性成本，自托管约为每节点每月 $0.53，或通过 Pecunia 为 $1.76。运行 oracle sidecar（Section 10）增加了第二个收入流，该收入基于收入，随实际平台使用量缩放，由开发者消耗而非发行提供资金。

### 贡献者经济学

无法或选择不运行基础设施的运营者可以向现有节点贡献质押，分布于最多 10 个贡献者槽位。运营者可以在剩余部分按比例在贡献者之间分配之前收取区块奖励的 0% 至 10%。贡献者不承担托管成本，因此在每个价格点，贡献者的净收益都超过自托管或 Pecunia 托管运营者的收益。

### 节点生命周期

在维持抵押品和性能要求的情况下，节点无限期保持活跃。脱离合规的节点可以无惩罚地补救。如果未补救，强制注销将触发 14 天解绑期，无奖励。自愿退出需要 14 天解绑期，期间奖励持续。

## 5. 网络生存能力与攻击向量

### 生存能力要求

EXIOM 网络向开发者做出可靠性承诺。一个可以被单个数据中心停机击垮的网络无法做出这些承诺。协议强制执行最大故障域规模：没有任何单个物理设施、数据中心或路由集群可以托管超过 30% 的活跃节点。

在 943 个节点（September 27, 2026）的情况下，30% 约为 283 个节点。失去任何单个设施最多可以同时使 283 个节点离线，留下至少 660 个节点运营，足以维持区块生产和法定人数形成而不引发级联注销。这是一项工程要求，而非去中心化偏好。

### 两次硬分叉

生存能力强制执行分两个阶段交付，分开以降低风险并立即交付已验证的工作。

**HF22，已激活：** 运营者钱包密钥法定人数去重和解绑期统一，加上一个 Pulse 停滞恢复修订版（snode_revision 1），用基于签名的回退取代了早期的工作量证明恢复回退。无 Lokinet 依赖。通过 20 个停滞/恢复周期验证，恢复率 100%，零干预，最差区块间隔为 83 秒。HF22 在主网区块 219120 激活；停滞恢复修订版于 October 18, 2026 在区块 236920 激活。

**HF23，设计中，目标 Q4 2026：** 邻近集群注册上限、超额节点的零奖励调节因子，以及将法定人数去重从钱包密钥升级为邻近集群。这三者都依赖 Lokinet 路由图作为邻近信号。为避免在引入新传输层的那一刻就使其成为共识关键，Lokinet 首先在一个单独的非强制版本中发布（与 SQLite 轻节点存储变更一起），在该版本中邻近聚类已上线且可观测，但没有奖励后果。HF23 随后在该版本充分浸泡、测量了真实集群数量并调整了阈值和回退后，开启强制执行。

### HF22 控制措施

**运营者钱包密钥法定人数去重。** 在任何给定的 Pulse 轮次、oracle 会话或义务法定人数中，每个运营者钱包地址最多只能有一个节点持有验证者席位。如果随机抽取选中了来自同一运营者地址的两个节点，第二个将被来自不同运营者的节点替换。区块奖励不受影响；它们按等待时间排序分配，独立于法定人数参与。

已知局限：可被钱包拆分击败。使用多个钱包地址的运营者向协议呈现多个运营者密钥。HF23 通过邻近集群去重弥补这一缺口。

**解绑期统一。** 强制注销解绑期从 7 天延长至 14 天，与自愿退出匹配。两种情况现在都是 14 天。

### HF23 控制措施

一旦 Lokinet 作为网络传输层激活，物理上共置的节点将显示出特征性的路由签名：亚毫秒级的相互延迟和通过 Lokinet 路由图的高路径重叠。位于真正不同设施的节点将显示出更高的延迟和更低的路径重叠。这一聚类信号源自可观测的网络行为，不要求运营者披露其提供商或位置。

**集群注册上限。** 新节点注册将根据 Lokinet 路由邻近性与现有集群进行评估。如果目标集群已包含 30% 或以上的活跃节点，则协议拒绝该注册。

**零奖励调节因子。** 超过集群上限阈值的节点赚取零区块奖励，直到迁移到非集中的集群。节点在每个集群内按注册时长排序；最旧的节点在上限阈值内赚取完整奖励。超过该阈值的每个节点赚取零。降低的费率可以相对于 VPS 成本合理化；零则不能。

HF23 激活时适用 30 天宽限期。在宽限期内所有节点都赚取完整奖励。到期时，零奖励调节因子在超额节点上激活。

**邻近集群法定人数去重。** 将 HF22 钱包密钥去重升级为邻近集群去重。每轮每个邻近集群最多一个节点，无论钱包结构如何。弥补钱包拆分缺口。

每轮法定人数规模为 12 个席位。因此去重需要至少 12 个不同的邻近集群才能在无回退的情况下运作。鉴于当前网络拓扑，HF23 激活时的集群数量可能接近这一最小值。算法实现了强制回退：如果在填满 12 个席位之前所有不同集群都已耗尽，则额外席位从最小（最不集中）的集群开始分配，然后最集中的集群才获得第二个席位。回退频率被记录并在节点浏览器中作为实时集中度风险指标发布。一个从不触发回退的网络已实现足够的物理多样性。

### 其他控制措施

**资本成本壁垒。** 100,000 XEQM 的最低运营者质押确保每个运营者为每个节点投入真实资本。运行 N 个节点需要至少 N x 100,000 XEQM 的质押。

**运营者费用捕获保护。** EXIOM 不受某些服务节点网络中存在的运营者费用捕获攻击的影响，在这种攻击中，运营者以极少的资本注册节点并设置 100% 的费用，以捕获整个区块奖励，无论贡献者质押如何。最高费用上限为 10%，且 50% 的最低运营者质押使这种做法在经济上不合理。

**正常运行时间证明时序分析。** 位于同一物理主机上的节点以紧密相关的集群提交正常运行时间证明，无需守护进程变更即可从现有证明接收数据中检测到。

**ASN 分析。** 同一自治系统编号背后的节点共享提供商级基础设施和法律风险敞口。ASN 集中度有助于集群分配和治理审查。

**治理黑名单。** 一个由治理管理的公钥黑名单阻止被列入黑名单的注册密钥注册新节点。

**Nakamoto 系数目标。** 网络的目标是运营者系数至少为 8。截至 September 27, 2026，在 943 个活跃服务节点和 204 个运营者中，运营者 Nakamoto 系数 — 即控制多数活跃节点的最小运营者数量 — 为 9，达到目标（高于 July 2026 的 184 个运营者中的 7）。物理设施集中度是一个独立且更为紧迫的问题：单个数据中心区域仍托管着多数节点，而这正是 HF23 的邻近集群上限旨在打破的集中度。

完整的集中度限制提案见 [concentration-limits-proposal.md](https://github.com/XEQMLabs/whitepaper/blob/main/concentration-limits-proposal.md)。女巫抵抗方法论见 [XEQMLabs/xeqm-sybil-resistance](https://github.com/XEQMLabs/xeqm-sybil-resistance)。

### Lokinet 作为未来的网络传输层

EXIOM 网络的寻址基础设施将从公开宣告的 IP 地址迁移到 Lokinet 寻址。Lokinet 首先在 HF23 之前（目标 Q4 2026）以非强制版本发布；HF23 随后添加使用 Lokinet 路由图的集中度强制执行。Lokinet（低延迟匿名路由协议，LLARP）是一个 layer 3 洋葱路由协议，通过多跳洋葱路由将任何基于 IP 的流量路由经过多个服务节点，路径中没有任何单个节点同时知道源和目的地。

一旦 Lokinet 激活：

- 服务节点将通过其 Lokinet 加密标识符而非公开宣告的 IP 地址寻址
- EXIOM 开发者 API 将作为隐藏服务在 `.loki` 地址可访问，向 API 节点隐藏开发者的源 IP
- RFQ 交易平台将作为隐藏服务可访问，向平台隐藏请求者和 LP 的 IP 地址
- 证明者和验证者法定人数之间的 oracle 会话通信将通过 Lokinet 路由，消除中心化协调者信任假设

Lokinet 在 HF23 之前以非强制版本发布，目标为 Q4 2026，HF23 在其充分浸泡后跟进。LLARP 代码库已存在于 EXIOM 代码库中；将 Lokinet 作为主要网络传输层的实施始于 Q4 2026。

## 6. XEQM 作为实用代币

XEQM 需求来自三个来源。节点质押锁定了最大份额的供应量，在当前 943 个活跃节点（September 27, 2026）的情况下约为 68%。开发者消耗创造了一个持续的流通速度层：应用程序以 XEQM 支付生产 API 使用费用，因此平台采用直接转化为对代币的经常性需求。oracle 访问为更高交易量的消费者增加了第三层。

访问遵循预付费、基于使用量的模型，而非质押解锁门槛 — 开发者不必获取并锁定固定质押即可构建：

| 层级 | 访问模型 |
|---|---|
| 免费 | 零成本构建和评估：慷慨的月度调用额度，无需存款 |
| 生产 | 预付费使用：存入 XEQM 并按调用付费；webhooks 和更高限额 |
| 企业 | 自定义限额、SLA 和支持；批量条款 |

生产使用按每次 API 调用计量，并从开发者的预付 XEQM 余额中扣减。存款不可退还，随着被消耗而确认为平台收入（见 Section 3）。早期的设计将层级设在固定 XEQM 质押之后；该设计已被这一预付费模型取代，后者对开发者更简单，且为商业 API 的标准做法。

## 9. 路线图

**Phase 1，网络稳定化。已完成。** 服务节点网络截至 September 27, 2026 增长到 943 个活跃服务节点（从 July 2026 的 184 个运营者中的 693 个，Nakamoto 系数 7）。XEQ 至 XEQM 代币互换成功运行并结束。

**Phase 2，EXIOM 开发者 API 和 EXIOM Oracle。进行中。** EXIOM Oracle 已在主网上线并设有运营者委员会，开发者 API 处于测试版（自助凭据、合规和验证端点、OpenAPI）。剩余的 Phase 2 工作：预付费消耗计费、运营者收入分成，以及首批生产集成。EXIOM RFQ 交易平台的开发并行进行，XEQM/BTC 为首个交易对。

**Phase 3，EXIOM Privacy Oracle 和 RFQ 平台。** oracle 分阶段推出：内部概念验证、联合测试网，然后是带有内部消费者的主网。RFQ 交易平台在此阶段达到生产状态，使用 oracle 为 XEQM/BTC 交易对进行私有价格证明。两者都基于 EXIOM API 构建。

**Phase 4，外部 oracle 消费者访问。** oracle 输出可供生产层和企业层开发者及外部消费者使用。Nakamoto 系数阈值 6 已达到；激活以 Phase 3 完成为前提。

**HF22，已激活（主网区块 219120）。** 两项无 Lokinet 依赖的共识变更，运营者钱包密钥法定人数去重（每轮每个法定人数席位一个运营者地址）和解绑期统一（强制注销从 7 天延长至 14 天），加上一个 Pulse 停滞恢复修订版（snode_revision 1），该修订版于 October 18, 2026 在区块 236920 激活，用基于签名的回退取代工作量证明恢复。经过 20 个停滞/恢复周期验证（100% 恢复，最差区块间隔 83 秒）。

**Lokinet 和轻节点版本，HF23 之前。** 一个非强制版本，将 Lokinet 作为网络传输层上线（邻近聚类在节点浏览器中上线且可观测，无奖励后果），并引入 SQLite 轻节点存储（降低每节点内存和磁盘，并可选近期窗口轻节点）。该版本充分浸泡，以便在任何强制执行生效之前测量真实的邻近集群数量并调整 HF23 阈值和回退。

**HF23，设计中，目标 Q4 2026。** 在上述非强制的 Lokinet 和轻节点版本充分浸泡后开启强制执行：邻近集群注册上限（当集群超过活跃节点的 30% 时拒绝注册）；对超过上限阈值的节点的零奖励调节因子，按注册时长排序；将法定人数去重从钱包密钥升级为邻近集群，并有一条强制回退规则，确保即使存在的不同集群少于 12 个也始终能够形成法定人数（最小的集群在最集中的集群之前先获得额外席位，回退频率作为集中度风险指标被记录和发布）。激活时适用 30 天宽限期，之后零奖励调节因子才生效。

**Phase 6，正式治理。** 结构化提案流程、运营者加权投票、长期过渡远离创始团队治理。

## 10. EXIOM Oracle

### 首个上线的 oracle：EXIOM Oracle

平台的首款 oracle 产品已在主网上线。EXIOM Oracle 是一个由 XEQM 服务节点运营者组成的委员会 — 每人在其节点旁运行一个轻量级 oracle sidecar — 共同生成关于合规事实的 BLS 聚合、EIP-712 签名证明，最直接的是某个地址是否符合给定司法管辖区的资格。应用程序通过开发者 API 使用这些证明，并可将签名结果提交到链上。委员会部署在 Robinhood Chain（chainId 4663）上，截至 September 28, 2026 运行一个 12 名成员的运营者委员会，签名阈值为三分之二（12 个中的 8 个）。

**安全模型：注册集合与阈值。** EXIOM Oracle 不对每轮委员会进行抽样。由于一个 BLS 聚合无论是 8 名成员还是 800 名成员签名，对门控的验证成本相同，因此每个注册成员每轮都签名；抽样子集毫无益处，并会重新引入不幸的抽取恰好包含足够多串通成员以伪造的风险。因此安全性归结为规模为 N 的注册成员集合的两个属性，在门控强制执行的三分之二阈值 k = ceil(2N/3) 下：

- **伪造** 要求对手控制至少 k 名注册成员 — 一种串通，因此是一个**运营者**集中度的问题。
- **停机**（活性失败）要求至少 N - k + 1 = floor(N/3) + 1 名注册成员同时下线 — 一次相关性停机，因此是一个**基础设施**集中度的问题。

这就是两个 Nakamoto 系数，它们是注册集合的属性，而非更广泛的服务节点集群的属性：集群的分布限制共识，而 oracle 的伪造和活性抵抗仅取决于谁持有注册席位。

**当前实现。** 截至 September 28, 2026，注册成员全部由项目运营者运营，因此 oracle 的运营者系数为 1：如今其伪造抵抗依赖于对单个运营者的信任，而非分布式密码学。这是诚实的起始状态。安全模型是跨独立运营者的 k-of-N；随着独立方加入，这一实现得到加固，这正是将额外服务节点运营者作为 sidecar 成员加入的目的。仅靠节点数量无济于事 — 额外成员只有在作为不同设施上的独立运营者时才能提高两个系数。

**多样性如何强制执行。** 由于没有每轮选择，多样性在**准入**时决定：只有当某成员使每个运营者的份额保持在 k 以下、每个设施的份额保持在 floor(N/3) 或以下时，该成员才被注册，且 k 随集合增长而被提高以跟踪 ceil(2N/3)。注册集合的集中度被持续监控，并作为伪造余量（k 减去最大运营者的份额）和活性余量（floor(N/3) + 1 减去最大设施的份额）发布；非正的余量即为警报。设施信号如今是 ASN 和正常运行时间证明到达时序，在 HF23 时将锐化为 Lokinet 路由邻近性，后者即使跨不同 ASN 也能检测物理共置。这些分布事实本身可通过 oracle 的类型化事实接口进行证明，因此集中度指标是一个委员会签名的值，而非单个受信任脚本的输出。

sidecar 刻意保持轻量：它仅持有自己的签名密钥，在本地读取其节点的身份，且从不处理运营者的花费密钥。运行它是服务节点运营者赚取 Section 3 和 Section 4 所述额外的、由使用量提供资金的收入的机制。

### 更广泛的愿景：EXIOM Privacy Oracle

EXIOM Privacy Oracle 允许应用程序使用经过认证的私有数据馈送，而不暴露底层源数据。它使用零知识证明技术来证明来自标准 HTTPS 端点的数据来源，不需要服务器端合作，也不需要受信任的硬件。它是一个 Phase 3 交付物，在 Phase 2 API 平台稳定化和完整构建开始前的密码学咨询之后。

oracle 不是通用数据馈送。它是一个隐私优先的 oracle，适用于数据本身必须保持机密的用例：在不透露确切价格的情况下证明价格阈值，在不暴露凭据的情况下证明账户余额，在不披露底层记录的情况下进行合规证明。EXIOM RFQ 平台是首个内部消费者，用它来证明 XEQM/BTC 成交发生在参考价格或更优价位，而不向平台或对方透露确切价格。

一旦 Lokinet 作为网络传输层激活，证明者和验证者法定人数之间的 oracle 会话通信将通过服务节点网络进行洋葱路由。证明者的来源和法定人数节点的网络地址都不会对任何单个中继节点可见，从而消除中心化协调者信任假设。

### 架构

**证明者层。** 持有私有数据源访问权限的应用程序或用户参与一个加密协议，该协议对 TLS 响应做出承诺而不透露它。凭据和原始数据从不离开证明者的控制。

**验证者层。** 一个轮换的服务节点法定人数验证已承诺数据是否满足请求的条件。验证者节点只了解结果（真或假、高于或低于阈值），从不看到底层数据或凭据。

**消费者层。** 消费者只接收最小输出：一个布尔结果、一个阈值比较、一个签名证明，或一个小的派生值。原始源数据从不发布。

### 分阶段构建计划

**Phase 1，内部概念验证。** 创始团队针对一小组白名单来源端到端验证完整的加密协议，无外部消费者或服务节点参与。

**Phase 2，联合 oracle 测试网。** 具有强正常运行时间历史的志愿服务节点运营者在测试网上加入验证者池。在任何主网部署之前对证明完整性进行对抗性测试。

**Phase 3，带有内部消费者的主网 oracle。** oracle 验证者职责向合格的主网节点开放。输出馈送给内部 EXIOM 合约和 RFQ 平台。oracle 费用开始流向参与的验证者节点。

**Phase 4，外部消费者访问。** oracle 输出可供生产层和企业层开发者及外部消费者使用。以 Phase 3 完成为前提。

### 验证者硬件要求

指示性要求：8 个 CPU 核心、16 GB RAM、200 GB SSD、500 Mbps 低延迟。标准 API 节点基准硬件不足以胜任 oracle 验证者职责。

| 收入来源 | 描述 |
|---|---|
| 区块奖励 | 标准服务节点区块奖励，不变 |
| 平台收入分成 | 运行 oracle sidecar 的运营者的开发者消耗收入按比例分成 |

## 11. EXIOM RFQ 交易平台

EXIOM RFQ 平台是一个具有加密结算证明的点对点场外交易系统，基于 EXIOM API 构建。首个交易对是 XEQM/BTC，二者均为原生 Layer 1 资产，无代币化、无封装、无跨链桥风险。

一旦 Lokinet 激活，RFQ 平台将作为 Lokinet 隐藏服务可访问。请求者和 LP 的 IP 地址都不会对平台可见。oracle 定价层允许交易对手证明成交发生在来自白名单来源的参考价格或更优价位，而不向平台或对方透露确切成交价格。

RFQ 应用规范和数据模型已完成。活跃开发在 Phase 2 的 API 层进行。完整交易平台的生产是一个 Phase 3 交付物，取决于 EXIOM API 达到生产状态以及 oracle MVP 完成其内部概念验证。
